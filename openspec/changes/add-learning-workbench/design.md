# 设计：稳定化中文学习工作台

## Context

`scripts/learning-library-collector.mjs` 已经实现 GitHub Trending/Search/Release、Hugging Face 论文、RSS 技术文章和社区讨论采集，使用模型筛选 4 个仓库、2 篇文章、2 个社区讨论，读取仓库与正文证据，分别生成 8 篇学习笔记，再通过 Inkstone MCP 写入 1 篇索引。它还保留当日 pending、生成缓存、成功日期和 60 天 seen 状态。

当前缺口集中在运营可靠性而非基础功能：候选只按各来源自己的 `id` 去重，不能稳定识别跨入口重复；运行状态散落在控制台日志和多个文件中；现有测试只覆盖 RSS 与 Git 树解析；旧 GitHub Trending 和 AI Frontier timer 仍有独立的部署单元。用户要求分批开发，第一批只把“独立中文 Markdown、中文目录与标签、原始链接、去重、每日 6–10 条精选、索引和定时失败记录”做实，不引入新的产品界面。

## Goals / Non-Goals

**Goals：**

- 在现有实现上补强，而不是复制采集、报告生成或 MCP 写入逻辑。
- 默认稳定生成 8 篇高质量独立笔记，质量不足时明确失败。
- 对同一仓库、文章和讨论建立跨来源稳定标识。
- 让每次运行可以从一个安全的结构化状态文件判断阶段、结果和失败原因。
- 用自动化测试锁定用户可见的 Markdown、标签、索引、去重和重试行为。
- 将生产定时任务安全收敛到统一采集器，同时保留无损回滚路径。

**Non-Goals：**

- 修改 Inkstone 数据模型、MCP 协议或现有笔记编辑体验。
- 在第一批增加学习看板、来源配置页面或阅读进度。
- 改变每天默认 4/2/2 的来源比例。
- 自动清理历史聚合笔记或旧状态目录。
- 自动执行生产部署；生产变更必须在本地验证和审查通过后单独进行。

## Decisions

### 1. 继续使用独立采集进程和 MCP 边界

**Choice：** 保留 systemd oneshot + timer 和现有 MCP 写入方式；第一批不把采集逻辑移入 Inkstone API 或数据库调度器。

**Rationale：** 现有采集器已经上线验证，MCP 提供权限受限、幂等的笔记写入边界。独立进程可单独重试和升级，不扩大 Inkstone 主服务的故障面。

**Alternatives：** 新增数据库任务表与管理 UI；使用 Inkstone 内置 scheduler。两者会引入 API、迁移、权限和界面工作，超出第一批范围。

**Consequences：** 运行状态保存在受保护的 `StateDirectory`，主要运维入口仍是 systemd 与文档；后续可以在不改变流水线语义的前提下增加管理界面。

### 2. 将来源标识和内容标识分离

**Choice：** 保留来源 `id` 用于审计，同时新增 `contentKey` 用于去重。GitHub 仓库统一为小写 `owner/repo`；普通网页使用规范化 URL，移除片段、常见跟踪参数、默认端口和无意义尾斜杠；社区讨论同时保留讨论链接和原文链接，并以材料主体生成内容键。

**Rationale：** Trending、Search 和 Release 会给同一仓库产生不同来源 ID，RSS 聚合器也可能改变 GUID 或附加跟踪参数。单独的内容键能在不丢失来源信息的情况下阻止重复选题。

**Alternatives：** 仅依赖 LLM 识别语义重复；仅使用 RSS GUID。前者不可确定且难以测试，后者无法覆盖跨源与 URL 变体。

**Consequences：** 仓库的普通条目和版本发布默认视为同一学习主体；如未来确实需要同时学习重大版本，应显式引入“版本专题”类型，而不是绕过去重。

### 3. 固定默认 8 篇并让质量不足显式失败

**Choice：** 第一批继续固定 4 个仓库、2 篇文章和 2 个社区讨论，总计 8 篇；候选池不足或模型选择不符合约束时不降级为低质量占位内容。

**Rationale：** 8 位于用户要求的每日 6–10 条范围内，并已经与报告生成、索引和阅读时间匹配。固定配额使验证和阅读预期稳定。

**Alternatives：** 每天动态生成 6–10 篇；来源失败时自动减少数量。动态配额会增加选择规则与索引不确定性，且可能掩盖长期失效的数据源。

**Consequences：** 严重来源故障会导致当日没有新内容，但运行记录会给出可行动的失败原因；不会用低价值内容换取表面成功。

### 4. 使用原子运行记录描述状态机

**Choice：** 每日维护一个原子写入的运行记录，阶段至少包括 `collecting`、`selecting`、`enriching`、`generating`、`writing-notes`、`writing-index`、`succeeded` 和 `failed`。记录只保存计数、来源名称、清理后的错误和时间，不保存候选正文、令牌或请求头。

**Rationale：** 单一记录能回答“是否运行、卡在哪一步、是否可重试、写入多少”，同时避免解析 journal 或多个缓存文件。原子替换避免进程终止留下半个 JSON。

**Alternatives：** 只依赖 systemd journal；新增数据库运行表。前者不适合自动检查，后者扩大主应用数据模型与备份边界。

**Consequences：** 状态文件属于运行时数据，不进入 Git；重试会更新同一日期记录并增加尝试次数，保留最近一次失败摘要。

### 5. 继续使用稳定 MCP operation_id 实现可续跑

**Choice：** 在远程写入前保留完整 pending 和逐条报告缓存；每篇笔记及索引继续使用日期和顺序派生的稳定 `operation_id`，索引最后写入，成功标记最后更新。

**Rationale：** 该机制已经存在，补测比重新设计分布式事务更低风险。MCP 幂等操作使重试可以复用之前成功创建的笔记。

**Alternatives：** 在 Inkstone 中增加批量事务写接口；失败时删除已写笔记。前者改变公共边界，后者可能误删用户已经打开或编辑的内容。

**Consequences：** 恢复过程中可能暂时存在尚未被索引链接的独立笔记，但最终索引只在全部引用就绪后创建；不会自动删除部分成功数据。

### 6. 用显式无损切换替代隐式并存

**Choice：** 提供幂等切换脚本或逐条等价命令：安装/更新统一 service 和 timer，执行 daemon-reload，启用统一 timer，停用 `inkstone-github-trending.timer` 与 `inkstone-ai-frontier.timer`，随后检查 `list-timers` 和服务状态。回滚只改变 enablement，不删除单元、状态或笔记。

**Rationale：** 仅修改仓库里的 unit 文件不会影响服务器上已经启用的旧 timer。显式切换才能避免新旧采集器同时运行。

**Alternatives：** 删除旧 unit 和状态；让所有采集器并行。删除会降低可恢复性，并行会继续生成用户不想要的聚合内容。

**Consequences：** 部署需要 systemd 管理权限，必须在代码审查和本地验证完成后单独授权执行。

## Risks / Verification Evidence

- **[URL 规范化误合并不同内容]**：对 GitHub、普通文章、社区讨论、查询参数白名单和国际化 URL 使用固定夹具测试；只移除明确的跟踪参数。
- **[URL 规范化漏掉重复内容]**：对 Trending/Search/Release 和常见 RSS 重定向形式增加跨来源测试，并在运行记录中输出去重前后计数。
- **[模型仍可能产生泛泛报告]**：保留结构验证，并以固定报告夹具测试必需章节、中文标签、原始链接与真实代码路径约束；生产抽样作为部署验收证据。
- **[中途失败产生部分笔记]**：故障注入测试在每个写入边界中断并重跑，验证稳定 operation ID、pending 复用和最终索引完整性。
- **[错误记录泄漏凭据]**：错误清理测试覆盖 Bearer Token、Authorization 头和凭据路径内容，运行记录只允许结构化安全字段。
- **[切换影响旧数据]**：切换脚本测试或静态验证禁止 `rm` 和数据目录删除；生产前记录 timer 状态，切换后验证，回滚只恢复 enablement。

## Rollout and Rollback

1. 本地完成纯函数、渲染、运行记录和故障注入测试，并运行 Inkstone 全量单元测试与 VPS 构建。
2. 提交并推送经审查的精确 Git 版本。
3. 在 VPS 记录当前启用的相关 timer、代码版本和最近成功状态，备份 systemd 单元与采集状态目录。
4. 部署精确提交，安装更新后的统一 service/timer，执行无损切换并手动触发一次。
5. 验证 8 篇独立笔记、1 篇索引、中文目录/标签、来源链接、运行记录、journal 和次日 timer。
6. 若验证失败，停用统一 timer，恢复部署前的 unit 与旧 timer enablement；保留所有笔记和状态用于排查。
